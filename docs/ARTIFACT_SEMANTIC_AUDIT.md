# AETHRION Native Artifact Semantic Audit

The family audit is read-only. Run it from the repository root:

```bash
python -m aethrion.family_audit --root . --output reports/model-family-readiness.json
```

It reports all eleven native model entries and keeps three concepts separate:

- **Artifact integrity:** presence, non-zero size, and registered SHA-256 match.
- **Semantic integrity:** report identity/provenance, tokenizer and processor structure, and checkpoint tensor compatibility with the declared architecture.
- **Training/release state:** the registry's explicit status and independent release gates. Semantic checks never change this status.

## Checkpoint validation

Checkpoint loading uses PyTorch's `weights_only=True` mode. The audit checks the expected AETHRION checkpoint format, model ID where applicable, model configuration, non-negative step, exact state-dictionary keys and tensor shapes, and finite floating-point weights. It does not run inference or training.

## Tokenizer format

Text-capable models use `aethrion-byte-bpe-v1`. The byte-BPE loader validates the merge graph and vocabulary bounds. The resulting vocabulary must not exceed the model configuration's `vocab_size`. The vocoder does not require a tokenizer.

## Processor format

Models with a modality processor use a JSON object with this contract:

```json
{
  "format": "aethrion-processor-v1",
  "model_id": "vision",
  "modality": "vision",
  "config": {
    "processor-specific": "settings"
  }
}
```

The model ID and modality must match the specialist registry; `config` must be a non-empty object. This is a structural contract, not evidence of training-data approval or model quality.

## Cross-artifact consistency

When reports and checkpoints exist, the audit compares model IDs, dataset SHA-256, checkpoint SHA-256, and step counters. Specialist report `steps` is a completed-step count, so it must equal checkpoint `step + 1`; BASE chat reports use the zero-based `step` value.

The output field `trained_claim_supported` remains false. Only the independent governance, evaluation, safety, and human-release process can authorize a registry transition. Missing artifacts, unregistered hashes, invalid schemas, and mismatches remain visible as failures; no files or approvals are generated by this audit.
